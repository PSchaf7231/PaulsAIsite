# Listing storage and search — November 6, 2026 (supersedes the single-row snapshot below)

**Why it changed:** the build downloaded all ~13,200 eligible homes from Spark in ~121 s, then tried to save them as one JSONB value (an estimated 70–100 MB) in `ListingSnapshot`. That single write hung for 18+ minutes and the deploy was cancelled. Every visitor read also loaded the whole value, so pages were slow and detail pages could time out (500).

**Storage now:** `MlsListing` holds one row per home (primary key = Spark `ListingKey`, unique normalized MLS number `mlsKey`). Indexed columns: active, type, price, city, ZIP, beds, baths, property type, latitude/longitude, pool/waterfront/garage, address search text and modification time. `summary` (JSONB) is the compact card (first photo, no remarks); `detail` (JSONB) holds all photo URLs and the full remarks and is read only by the detail page. `MlsSyncStatus` (id = 1) records the last run, last success, last complete sync, counts and the last error. `ListingSnapshot` is left untouched for rollback; nothing writes it any more. The migration `20261106120000_mls_listing_rows` is additive only (two new tables, indexes, RLS like the other tables).

**Sync (build script and hourly cron):** download as before, then compare each home's modification time with the stored row. Only new or changed homes are upserted, 250 rows per `INSERT … SELECT FROM unnest(…)` statement; unchanged homes only get `lastSeenAt` touched. When every changed row is written, homes missing from the pull are marked inactive (skipped if the pull is under half of the stored inventory; inactive rows older than 30 days are deleted). Work stops cleanly at a time budget (cron 255 s, build 420 s by default, `LISTING_SYNC_BUILD_BUDGET_MS`) and the next run resumes, because rows are independent. The build script never fails the build: if MLS or the database is unavailable it logs the reason and the deploy serves the rows already stored. It skips the download when a complete sync finished within 2 hours (`LISTING_SYNC_FORCE=1` overrides).

**Reads:** every search path runs one indexed SQL query with WHERE / ORDER BY (stable `listingKey` tiebreak) / LIMIT 24 / OFFSET plus a count: `/listings` (server render), `/api/listings` (filters, sorting, paging), the homepage search form and featured homes, community pages (now 24 cards), Madison/Pax searches, typed searches. Typed searches recognise cities (including every city present in the stored inventory), ZIP codes, street addresses and MLS numbers (address/ZIP/MLS match `searchText`); a phrase with nothing recognisable falls back to the unfiltered search as before. `/api/listings/map` returns lightweight pins only (id, slug, address, city, price, type, coordinates) for every match, or only those inside `north/south/east/west` when given. Detail pages read one row by MLS number; if the row is missing or the database is unreachable they ask Spark for that single listing. Data is served while the last successful sync is under 26 hours old.

# Listing performance — November 5, 2026

Search and detail requests read a shared PostgreSQL snapshot instead of calling Spark per visitor. The initial listing page contains the count and up to 24 cards in server-rendered HTML. Subsequent pages also contain 24 cards. Sorting runs across the complete stored inventory before pagination; cards paginate independently of the map. The map endpoint returns compact coordinates, prices and property links for every matching home in the snapshot, without a 24/200/500 cap. The browser selects homes in the visible area and groups nearby pins. Each group exposes paginated property links, including homes at identical coordinates. Moving the map does not change the card search. Missing coordinates are disclosed rather than invented.

Fresh visits default to SALE, $750,000–$9,999,999, ascending price. Campaign tracking parameters do not remove those defaults. Explicit searches retain their requested filters. Reset still clears everything, including the typed query, using `/listings?all=1`.

Search buttons immediately show progress, searches scroll to the results, and loading never displays the empty-results message. Common typed queries use the existing local filter parser; otherwise AI interpretation has an 800 ms timeout. This parser supports city, budget, beds/baths and selected features, not arbitrary semantic property matching. Map code loads near the visible map; Madison's wrapper loads after the initial render or immediately when requested. The Anam embed and session startup are unchanged.

## Production setup

1. Vercel → pauls-a-isite → Settings → Environment Variables: add `CRON_SECRET`, a new random password of at least 32 characters, to Production. Do not use a CRM API key.
2. Keep the existing MLS credentials and PostgreSQL connection settings in Vercel. This uses the existing database; no new hosted service is required.
3. Build Command must use `npm run build`. It deploys the migration, generates Prisma, creates the initial complete MLS snapshot, and builds Next using webpack. A production MLS build fails if CRON_SECRET is missing or the initial refresh fails, keeping the previous deployment in place instead of publishing an unusable cache.
4. Deploy main. In the build logs, look for `Listing snapshot: { count: ..., checkedAt: ... }` and confirm the deployment is Ready and assigned to www.pbrealestatepros.com.
5. Vercel → project → Cron Jobs: confirm `/api/cron/listings` is registered. `vercel.json` schedules it hourly, at the top of each hour. Vercel supplies the Authorization header from CRON_SECRET. After adding or changing environment variables, redeploy.

Hourly refresh is enabled following Paul’s confirmed upgrade to Vercel Pro. After successful scheduled runs, inventory normally lags the source by up to about an hour plus refresh duration. This improves freshness; it does not itself reduce Anam voice latency. Failed refreshes preserve the previous complete snapshot; snapshots older than 26 hours are not displayed. Monitor failed cron executions in Vercel and retry from the Cron Jobs interface. A long MLS scan fails safely after roughly four minutes; it does not publish a truncated collection. If inventory grows beyond that budget, the sync must be split into resumable scheduled batches.

The replica stores full detail photos. Public card responses include only the first photo. A 30-second per-instance memory cache reduces repeated database transfers. Refresh publication is one atomic upsert, and an advisory lock prevents simultaneous refresh jobs.
